# UI Feedback Polish Plan

## Goal
Polish the frontend feedback in two places:
1. Make the processing status/progress bar feel more alive instead of static.
2. Turn the progress bar green after successful completion.
3. Change the crop frame border color to `#38BDF8`.

## Current Findings
- `ui/src/components/QueueList.jsx` renders one `ProgressBar` per queue item.
- `ui/src/components/ProgressBar.jsx` is currently static: it only sets width from `value` and has no status-aware styling.
- `ui/src/App.css` defines `.progress-track` and `.progress-value`, but they are visually minimal and non-animated.
- `ui/src/components/VideoRangeEditor.jsx` renders the crop overlay frame with class `.crop-frame`.
- `ui/src/App.css` currently styles `.crop-frame` with a yellow border (`rgba(250, 204, 21, 0.95)`).
- `ui/src/components/StatusPanel.jsx` exists, but it is not mounted in `ui/src/App.jsx`. Because of that, the user request most likely applies to the per-item queue progress bars rather than a separate global status widget.

## Implementation Plan
1. Make `ProgressBar` status-aware.
- Extend `ui/src/components/ProgressBar.jsx` to accept the queue item status in addition to the numeric progress value.
- Normalize/clamp the value before rendering so visual state stays predictable.
- Add status modifier classes on the track/fill elements so CSS can distinguish `queued`, `uploading`, `processing`, `success`, and `error` states cleanly.

2. Pass queue status into the progress bar.
- Update `ui/src/components/QueueList.jsx` so each rendered progress bar receives both `item.progress` and `item.status`.
- Keep the change minimal and local to the queue list instead of introducing new state layers.

3. Make the bar feel more alive in CSS.
- Update `ui/src/App.css` for `.progress-track` and `.progress-value`.
- Add smooth transitions for width, background, and shadow so the bar no longer jumps visually.
- Add a subtle active-state treatment for `uploading`/`processing`, such as a moving highlight or soft pulse, while keeping it restrained and readable.
- Keep inactive states muted so only active work draws attention.

4. Add a distinct success color.
- Introduce a dedicated success modifier in `ui/src/App.css` that turns the completed bar green once `status === 'success'`.
- Stop any active animation in the success state so the finished item reads as complete rather than still running.
- Keep the filled value at `100%` visually aligned with the success state already produced by the queue flow in `ui/src/App.jsx`.

5. Update the crop frame accent color.
- Change `.crop-frame` in `ui/src/App.css` from the current yellow border to `#38BDF8`.
- Adjust the related glow/outline values around the frame if needed so the new blue border still has enough contrast against the dark preview.
- Preserve existing drag behavior and geometry logic in `ui/src/components/VideoRangeEditor.jsx`; only the visual treatment needs to change.

## Tests To Update
- Add or update focused tests for `ui/src/components/ProgressBar.jsx` to verify status-based class changes.
- If needed, add a small queue-level test path to confirm `QueueList` passes status through correctly.
- Update `ui/src/components/VideoRangeEditor.test.jsx` only if the crop-frame color is asserted there; otherwise the current geometry tests can remain unchanged.

## Validation Plan
- Run the relevant frontend test subset for the touched components after implementation.
- Do not perform manual runtime/browser verification unless explicitly requested, in line with the project instructions.

## Notes
- The most likely target for “status bar” is the queue item progress bar, because that is the only mounted status-progress UI in the current app.
- No backend or API changes are required for this task.
