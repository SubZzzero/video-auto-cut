# Plan: Fix manual time-input segment editing

## Goal
Fix the `HH:MM:SS` manual time inputs so segment replacement behaves predictably.

Example bug to eliminate:
- Selecting the minute `00` in `00:00:00` and typing `10` should keep the edit in the minutes segment and end at `00:10:00`.
- The input must not jump into seconds or reflow digits into an unintended time value while the user is still typing.

## Findings
- `ui/src/components/VideoRangeEditor.jsx` renders both time inputs as fully controlled fields with `value={formatClockValue(...)}`.
- `ui/src/App.jsx` immediately parses every `onChange` and writes the parsed seconds back into queue state.
- `ui/src/utils/time.js` parses by stripping all non-digits and right-aligning to six digits, which is useful for compact numeric input but interacts badly with partial segment edits inside a formatted string.
- The current flow causes a re-render after the first typed digit of a replacement, so the browser selection/caret context is lost before the second digit is entered.

## Implementation plan
1. Add a regression test first.
- Extend `ui/src/components/VideoRangeEditor.test.jsx` with a stateful harness or component-level interaction test.
- Use `@testing-library/user-event` to reproduce the real edit flow:
  - focus the start or end input
  - select only the minute segment
  - type `10`
  - assert the final visible value is `00:10:00` (or the equivalent expected time for the seeded value)
- Add at least one test that proves the existing bug and one that covers the sibling field so both start and end behaviors stay aligned.

2. Decouple the displayed draft text from the committed seconds value.
- Update `ui/src/components/VideoRangeEditor.jsx` to keep local draft state for the start and end time inputs while the user is editing.
- While an input is focused, render the local draft instead of immediately reformatting from `item.startTime` / `item.endTime`.
- Sync the local draft back from props when:
  - the field is not being edited, or
  - the value changes externally through sliders or queue-item switches.
- Keep the existing metric cards and sliders bound to canonical queue state so only the text-entry UX changes.

3. Commit typed values without clobbering the active edit.
- Preserve the raw typed string in the input on each `onChange`.
- Continue notifying the parent when the draft is parseable, but do not let the formatted parent value overwrite the focused field mid-edit.
- Normalize the visible value on blur so the field settles back to a stable `HH:MM:SS` string after editing completes.
- If the current implementation needs a small helper for draft syncing or commit logic, keep it local to `VideoRangeEditor.jsx` unless it is clearly reusable.

4. Keep compact numeric parsing support unless it conflicts with the fix.
- Retain existing `parseClockInput()` behavior for full numeric paste/use cases such as `215 -> 00:02:15`, unless implementation shows that a narrower parser is required.
- If parser behavior must be tightened, make the smallest change possible and cover it with focused unit tests in `ui/src/utils/time.test.js`.

5. Add focused utility coverage if parsing rules change.
- Extend `ui/src/utils/time.test.js` only if the parser or normalization rules are adjusted.
- Cover any new edge case introduced by the fix, such as formatted partial input handling or blur normalization.
