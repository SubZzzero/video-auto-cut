# Plan: add dynamic crop preview overlay with draggable crop position

## Goal
Add a real-time crop overlay to the local video preview so it appears only when a crop preset is selected, preserves the preset aspect ratio, supports dragging inside video bounds, and makes the dragged crop position affect the actual processed output.

## Current findings
- The selected crop preset already lives in per-file UI state as `activeItem.crop` and is updated through `handleCropChange()` in `ui/src/App.jsx`.
- `VideoRangeEditor.jsx` already owns the local preview `<video>` element, so it is the correct integration point for overlay rendering and pointer interaction.
- Frontend queue items currently store `crop`, `duration`, `startTime`, `endTime`, and `durationSeconds`, but they do not store source video dimensions or crop position.
- The frontend API client only sends `crop`, `duration`, `startTime`, and `endTime` in `ui/src/api/client.js`.
- The backend route, job store, schemas, and processor only know about preset-based crop. There is no persisted crop position in `api/routes/process.py`, `api/services/job_store.py`, `api/services/processing_service.py`, `app/schemas.py`, or `app/video/processor.py`.
- Backend crop math currently builds a deterministic window from the preset plus a fixed center in `app/video/crop.py` and `app/video/processor.py`.
- Existing backend tests already cover crop window generation, processor crop filters, job-store payloads, and process-route validation, which provides a clear place to extend coverage.
- Existing frontend tests cover `Controls.jsx`, but there are no focused tests yet for `VideoRangeEditor.jsx` overlay behavior.

## Chosen scope
Implement full drag end-to-end.

This means:
- the overlay appears and updates in real time in the UI
- the drag position is stored per file in frontend state
- the position is submitted through the API
- backend crop calculation uses the submitted position when building the actual ffmpeg crop filter

## Implementation plan
1. Extend the backend contract for crop position.
- Add crop position fields to the shared schemas and processing options, using explicit coordinates such as `cropX` and `cropY` in the public payload.
- Parse and validate the new form fields in `api/routes/process.py`.
- Persist them in `JobStore` and include them in job polling responses so queue state remains inspectable.
- Thread them through `process_job()` into `ProcessOptions`.

2. Update backend crop math to honor explicit placement.
- Refactor `app/video/crop.py` so crop-window calculation can accept a requested top-left position, clamp it safely inside frame bounds, and still derive width and height from the selected preset.
- Keep preset aspect-ratio logic centralized there so frontend and backend stay aligned.
- Preserve `none` behavior as a no-op.

3. Update processor logic to use the requested crop position.
- In `app/video/processor.py`, read frame size, resolve the selected crop dimensions for the preset, and build the crop filter from `cropX`/`cropY` instead of always using the centered window.
- Clamp invalid or stale coordinates against the actual source frame size so responsive frontend rounding cannot create out-of-bounds ffmpeg filters.
- Keep crop generation deterministic for every chunk in the selected range.

4. Expand backend automated coverage first.
- Update `tests/app/test_crop.py` for positioned crop windows and clamping behavior.
- Update `tests/app/test_processor.py` so processor-generated crop filters reflect submitted coordinates instead of the hardcoded midpoint.
- Update `tests/api/test_process_route.py`, `tests/api/test_job_store.py`, and `tests/api/test_processing_service.py` to cover the new fields and validation path.

5. Add frontend crop-ratio metadata and per-file crop position state.
- Centralize preset-to-ratio metadata in `ui/src/config/constants.js`.
- Extend queue-item defaults in `ui/src/App.jsx` and `ui/src/utils/queue.js` to store source dimensions plus crop position for each file.
- Initialize crop position to a centered value when metadata becomes available and when a preset is first selected.
- When the preset changes, recalculate crop box size and clamp or recenter position so the overlay remains valid.

6. Capture source video dimensions in the preview flow.
- Extend the local preview component to read `videoWidth` and `videoHeight` from `loadedmetadata`.
- Store those intrinsic dimensions in per-file state so drag can be converted between rendered pixels and source-space coordinates.
- Keep this metadata local-only; no backend roundtrip is needed.

7. Render a responsive overlay on top of the preview.
- Wrap the video element in a positioned preview shell inside `VideoRangeEditor.jsx`.
- Render the crop frame only when `crop !== 'none'`.
- Compute the displayed crop box from the intrinsic source dimensions, the selected aspect ratio, the stored source-space `cropX`/`cropY`, and the current rendered preview size.
- Add four mask regions to darken everything outside the crop box while keeping the inside clear.
- Add a visible border around the crop box and keep the whole layer clipped to the video radius.

8. Add drag interaction constrained to video bounds.
- Implement pointer-based dragging on the crop frame or overlay layer without adding a new dependency.
- Convert pointer movement from rendered pixels into source-space `cropX`/`cropY` updates.
- Clamp movement to the maximum valid travel distance for the current crop width and height.
- Keep interaction immediate on preset changes and while resizing the preview.
- Disable drag when no preset is selected.

9. Keep the overlay aligned during resize and preset changes.
- Measure the rendered preview box with a `ref` plus `ResizeObserver` or a browser-resize fallback.
- Recompute display geometry whenever preset, source dimensions, stored crop position, or rendered size changes.
- Ensure the overlay works for different source resolutions such as `1920x1080` and `1280x720` because calculations are derived from intrinsic dimensions rather than hardcoded sizes.

10. Add focused frontend tests for visibility, geometry, and drag state flow.
- Add or extend tests to verify no overlay for `none`.
- Verify preset selection shows the overlay and clearing the preset hides it.
- Verify switching presets changes the frame geometry.
- Verify drag updates the stored crop position callback and remains clamped inside bounds.
- Mock video metadata and layout measurement in jsdom for deterministic assertions.

## State model guidance
- `isPresetSelected`: derived from `crop !== 'none'`.
- `aspectRatio`: derived from centralized preset metadata.
- `position`: store real crop coordinates in source-space pixels as `cropX` and `cropY` per file, then derive rendered overlay coordinates from them.

Why source-space pixels are the safer contract:
- the backend already operates on real frame dimensions
- they map directly to ffmpeg crop coordinates
- they avoid ambiguity when the rendered preview is scaled responsively

## Assumptions
- `cropX` and `cropY` represent the crop window top-left corner in source-frame pixels.
- The smallest correct UX is to center the crop box by default, then preserve and clamp user-driven placement.
- No extra package is needed for drag; native pointer events, refs, and browser observers are sufficient.

## Risks to watch
- Frontend and backend can drift if preset ratio metadata is duplicated inconsistently.
- Drag math can become inaccurate if rendered coordinates are stored directly instead of source-space coordinates.
- Preset changes after a drag need explicit clamping or recentering, otherwise the overlay can end up outside bounds or disagree with backend output.
- jsdom does not provide real video layout, so tests must mock metadata and measurements deliberately.
