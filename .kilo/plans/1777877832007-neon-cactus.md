# Plan: add 4:5, 1:1, and 3:4 crop presets

## Goal
Add three new crop presets without breaking the existing `none`, `vertical`, and `horizontal` flow. Keep the change additive, backend-first, and limited to the current crop pipeline.

## Current findings
- UI crop options come from `ui/src/config/constants.js` and translated labels in `ui/src/i18n/translations.js`.
- API accepts crop values through `SUPPORTED_CROP_MODES` in `app/config.py` and `CropMode` in `app/schemas.py`.
- Backend crop math lives in `app/video/crop.py` and currently hardcodes only `vertical` and `horizontal` ratios.
- `VideoProcessor` already treats crop selection as a single deterministic preset, so new fixed ratios fit the existing flow cleanly.
- README documents the supported crop values and should be kept in sync.

## Implementation plan
1. Extend supported crop mode values in the backend.
- Update `app/config.py` to include new additive crop mode identifiers for `4:5`, `1:1`, and `3:4`.
- Keep existing modes unchanged for backward compatibility.
- Prefer ASCII-safe internal values such as `portrait_4_5`, `square_1_1`, and `portrait_3_4`, while exposing human-readable ratio labels in the UI.

2. Extend shared schema validation.
- Update `app/schemas.py` `CropMode` enum with the new values.
- This keeps job serialization, polling payloads, and in-memory job state aligned with the API contract.

3. Generalize crop ratio resolution in backend logic.
- Refactor `app/video/crop.py` so target ratios come from a single mapping instead of `if crop_mode == "vertical"` / `"horizontal"` branches.
- Keep the existing centered-crop behavior and even-dimension normalization.
- Preserve current `vertical` behavior while allowing the new portrait and square ratios to reuse the same path safely.

4. Expose the new presets in the UI.
- Update `ui/src/config/constants.js` `CROP_MODE_VALUES` to append the new crop modes.
- Update `ui/src/i18n/translations.js` crop labels for `en`, `ru`, and `ua` so the select shows `4:5`, `1:1`, and `3:4` clearly.
- Leave default form settings unchanged to avoid altering current startup behavior.

5. Keep documentation aligned.
- Update `README.md` supported crop mode descriptions so API usage and feature list reflect the new presets.

## Validation plan
1. Expand backend crop tests in `tests/app/test_crop.py`.
- Add assertions for new preset windows on a known source frame, such as `1920x1080`.
- Verify the new ratios produce stable, in-frame, even-sized crop windows.

2. Expand processor coverage in `tests/app/test_processor.py`.
- Add or parameterize a test to confirm a new crop mode produces the expected ffmpeg crop filter through `VideoProcessor`.
- Keep existing tests for `vertical` intact to catch regressions.

3. Run targeted automated checks only.
- Execute the relevant backend test subset for crop and processor behavior.
- Do not run manual app startup or install commands, per project rules, unless explicitly requested later.

## Expected impact
- Existing crop presets remain valid.
- New presets become selectable in the UI and accepted by the backend API.
- Crop output stays centered and deterministic, matching the current processing model.

## Risks to watch
- Using display ratios directly as raw API values would be noisier than stable slug values; internal slugs are safer.
- The current `vertical` special case in `app/video/crop.py` must not be removed in a way that changes its existing output dimensions.
- README and translation labels can drift if not updated together with the mode list.
