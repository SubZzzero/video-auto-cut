# Plan: add range-based trimming, custom segment length, and remove scene mode

## Goal
Process only a user-selected video range, split it into user-defined chunk lengths, expose a clear `HH:MM:SS`-style time UX with local duration awareness, and remove scene detection from the current product flow.

## Current findings
- Backend chunk splitting always processes `0 -> full duration` through `build_chunk_ranges()` in `app/video/splitter.py`.
- `VideoProcessor` still branches between `chunk` and `scenes`, and scene-specific logic is reflected in `app/schemas.py`, `app/config.py`, `api/routes/process.py`, `api/services/job_store.py`, translations, README, tests, and `requirements.txt`.
- The current API only accepts `mode`, `duration`, and `crop`; there is no request field for `startTime` or `endTime`.
- The frontend has no active range editor or duration-aware preview. `Controls.jsx` only exposes crop and numeric duration.
- Queue items currently store only file/job state, so any future time range needs either per-file settings or a second shared state model.
- `splitter.py` currently imports `get_video_duration()` from `app/video/scenes.py`, so scene removal should extract duration probing into a neutral helper instead of keeping chunk logic coupled to scene code.

## Implementation plan
1. Simplify the backend contract to chunk-only processing.
- Remove scene mode from the active API and processing path.
- Drop `ProcessMode`, `SUPPORTED_PROCESS_MODES`, mode validation, and scene-only progress/error copy where they are no longer needed.
- Update request/response schemas and job store fields so the public contract reflects a single trimming/splitting flow.
- Remove `PySceneDetect` references from README and `requirements.txt` as part of the feature de-scope.

2. Extract generic video duration probing away from scene helpers.
- Move total-duration logic into a neutral helper such as `app/video/metadata.py` or similar.
- Update chunk splitting and any other duration lookups to use the neutral helper.
- Remove or retire `app/video/scenes.py` and `tests/app/test_scenes.py` if they become dead code after the de-scope.

3. Extend processing inputs for range-based trimming.
- Add `start_time` and `end_time` to `ProcessOptions`, `/process` form parsing, job-store metadata, and polled job payloads.
- Serialize these as `startTime` and `endTime` in API responses to stay consistent with the current camelCase payload style.
- Validate `duration > 0`, `start_time >= 0`, and `end_time > start_time`.
- Keep `end_time` optional on the backend if helpful for resilience, but have the UI submit explicit values from local file metadata.

4. Refactor chunk-range generation to work inside the selected window only.
- Change `build_chunk_ranges()` to accept `range_start`, `range_end`, and `segment_duration`.
- Generate absolute source ranges clipped to the selected end time.
- Preserve the existing short-final-chunk behavior so the last output never extends past `endTime`.
- Update processor progress messages so they describe trimming the selected range instead of full-video or scene processing.

5. Keep processing scoped to the selected source range for performance.
- Continue using per-output ffmpeg trim commands with `-ss`/`-to` so each output only reads the requested source interval instead of processing the whole file.
- Avoid introducing a separate pre-trim intermediate file unless implementation reveals a concrete need; the minimal change is to constrain the existing trim commands to the selected ranges.

6. Update backend automated coverage around the new contract.
- Expand `tests/app/test_splitter.py` with partial-range, exact-boundary, short-selection, and invalid-range cases.
- Update `tests/app/test_processor.py` for chunk-only processing plus range propagation.
- Update `tests/api/test_process_route.py`, `tests/api/test_processing_service.py`, and `tests/api/test_job_store.py` to cover `startTime`/`endTime` fields and the removal of mode handling.
- Remove scene-mode expectations and scene-specific tests.

7. Add duration-aware local file state in the frontend.
- Extend queue items, or add a closely related per-file settings structure, to store `durationSeconds`, `startTime`, `endTime`, and `segmentDuration` per file.
- Populate duration from the local file via `loadedmetadata` on a browser `video` element rather than a backend metadata roundtrip.
- Keep batch support intact by storing settings per file, not one global range that may be invalid for other queued videos.

8. Add focused time parsing and formatting utilities.
- Create a small UI utility module for `HH:MM:SS` formatting, typed-input normalization, automatic colon insertion, second conversion, clamping, and selected-range duration calculation.
- Keep defaults centralized in `ui/src/config/constants.js` for values such as default segment duration and any time-input formatting constants.
- Add unit tests for typing behavior, parsing, and validation edge cases.

9. Build a small range editor component for manual input and slider interaction.
- Add a dedicated component such as `VideoRangeEditor.jsx` or `RangeControls.jsx` to keep `Controls.jsx` small.
- Render total video duration, current start/end, selected-range duration, manual time inputs, and synchronized slider controls.
- Use native inputs for the slider/timeline interaction instead of adding a new dependency, which avoids any install step.
- Surface inline validation when `endTime < startTime` or when typed values exceed the file duration.

10. Wire the frontend submission flow to the new API payload.
- Update `ui/src/api/client.js` to send `startTime`, `endTime`, `duration`, and `crop` without the removed `mode` field.
- Snapshot each file's effective settings before processing so the sequential queue remains deterministic even if the user edits another file afterward.
- Update queue/status presentation where useful so the active range is visible and understandable during processing.

11. Align copy and documentation with the new behavior.
- Update `ui/src/i18n/translations.js` for new range labels, helper text, validation messages, and revised progress text.
- Update `README.md` API docs and feature list to describe chunk-only range trimming with custom segment duration.
- Note during implementation that `plan.md` still mentions scene detection today; that file cannot be edited in this planning turn, but code/docs should follow the user-requested de-scope.

## Validation plan

## Assumptions
- Recommended direction: keep batch queue support by making time settings per file, not shared globally.
- Manual input should normalize to `HH:MM:SS` even though the request text says `HH:MM`; the provided example (`00:02:15`) clearly requires seconds.
- The smallest safe implementation is to remove scene mode from the user-facing flow and public contract, rather than keeping a hidden legacy mode.

## Risks to watch
- Batch processing becomes confusing if range settings stay global, because different files can have different durations.
- Removing scene mode touches multiple layers at once, so stale translation strings, README copy, or tests can easily drift if not cleaned together.
- Time-input masking can feel brittle if parsing and slider synchronization live inside components instead of a dedicated utility.
- If scene code is left partially referenced for duration probing, the de-scope will remain incomplete and harder to maintain.
