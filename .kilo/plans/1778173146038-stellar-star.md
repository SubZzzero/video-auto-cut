# Windows Installer Implementation Plan

## Goal
Convert the current local-only FastAPI + React project into a Windows-installable product that works out of the box without requiring the customer to install Python, Node.js, or FFmpeg manually.

## User-Requested Deliverables
1. Implement the packaging foundation in the codebase.
2. Prepare Windows packaging artifacts for the installer flow.
3. Create a separate `txt` file at the end with step-by-step Windows installer build instructions.

## Project Constraints
- Follow backend-first order.
- Do not run install commands without user approval.
- Do not rely on manual runtime verification unless the user explicitly requests it.
- Keep the current local-only architecture.
- Keep development flow intact while adding a production packaging path.

## Current Repo Gaps
### Production serving gap
The app currently depends on two development servers:
- FastAPI on `localhost:8000`
- Vite on `localhost:5173`

Current blockers in code:
- `ui/src/config/constants.js` hardcodes `http://localhost:8000`
- `ui/src/components/ResultList.jsx` hardcodes output links through the same base URL
- `api/main.py` only serves `/outputs`, not the built frontend
- `scripts/run_local.py` starts dev servers only

### Packaging gap
The backend currently assumes:
- `ffmpeg` is on `PATH`
- runtime directories live under the repo root
- the app is executed from a source checkout

These assumptions break for a Windows installer under `Program Files`.

## Recommended Shipping Shape
First sellable Windows release:
- keep the app as a local web app
- build React into static files
- serve the built UI from FastAPI
- package a Python launcher executable with PyInstaller `onedir`
- bundle `ffmpeg.exe` with the packaged app
- install through Inno Setup
- launch the app in the user browser from a local `127.0.0.1` URL

This is the smallest change set with the lowest delivery risk.

## Implementation Plan
### Phase 1: Backend production runtime
Purpose: make the backend self-sufficient in production before touching installer packaging.

#### 1. Extend runtime configuration in `app/config.py`
Add production-aware configuration helpers for:
- application root detection for source mode vs packaged mode
- UI build directory location
- writable runtime base directory
- outputs directory location
- temp directory location
- bundled FFmpeg directory location
- localhost host and port defaults for packaged launch

Recommended behavior:
- source mode on Linux/dev can continue using repo-relative directories
- packaged Windows mode should use `%LOCALAPPDATA%/VideoAutoCutter/`
- runtime directories should be created from config helpers, not hardcoded global paths only

Planned code impact:
- refactor `ROOT_DIR`, `OUTPUTS_DIR`, and `TEMP_DIR` into helpers or production-aware constants
- preserve current tests where possible, then expand them for Windows-style runtime paths

#### 2. Add bundled FFmpeg path resolution in `app/video/ffmpeg.py`
Replace direct `shutil.which("ffmpeg")` dependency with helper-based lookup:
- prefer bundled `ffmpeg.exe` from the packaged app directory
- fall back to `PATH` for development
- keep readable error messaging when FFmpeg is unavailable

Planned code impact:
- add a dedicated resolver for the ffmpeg executable path
- update command construction to use the resolved executable path instead of the literal `ffmpeg`

#### 3. Serve the built React app from FastAPI in `api/main.py`
Add production UI serving without breaking API routes.

Planned behavior:
- always keep `/process`, `/jobs/{job_id}`, `/health`, and `/outputs`
- if `ui/dist` exists, serve built frontend assets
- add SPA fallback route that returns `index.html` for non-API frontend paths
- keep CORS enabled only for dev-server use, not same-origin packaged mode

Planned code impact:
- keep API router registration first
- keep `/outputs` static mount
- add conditional frontend static serving only when a build exists
- add dev/production-aware CORS setup

#### 4. Add a packaged launcher entrypoint under `scripts/`
Create a production launcher that the packaged executable will run.

Planned launcher behavior:
- select a localhost port in a controlled way
- start the FastAPI app programmatically with Uvicorn
- wait until `/health` is available
- open the default browser to the app URL
- keep the process alive until the server exits

Recommended design:
- keep `scripts/run_local.py` for development
- add a separate packaged launcher such as `scripts/run_packaged.py`
- package the launcher, not the raw `uvicorn` CLI command

#### 5. Backend tests to add or update
Likely files:
- `tests/app/test_config.py`
- `tests/api/test_process_route.py`
- new backend tests for production UI serving and ffmpeg resolution

Validation targets:
- runtime directory helpers behave correctly
- ffmpeg resolver prefers bundled binary and falls back to `PATH`
- API routes still work when frontend static serving is enabled
- SPA fallback does not interfere with API endpoints

### Phase 2: Frontend production compatibility
Purpose: remove hardcoded backend URL assumptions so the same build works under same-origin serving.

#### 1. Replace hardcoded API base URL in `ui/src/config/constants.js`
Change the API base URL strategy to:
- use `import.meta.env.VITE_API_BASE_URL` when explicitly provided for development
- otherwise default to same-origin relative paths

Expected outcome:
- dev mode can still target FastAPI explicitly if needed
- packaged mode works with no hardcoded `localhost:8000`

#### 2. Update API and output link usage
Affected files:
- `ui/src/api/client.js`
- `ui/src/components/ResultList.jsx`

Planned behavior:
- API requests should work with relative `/process` and `/jobs/...`
- generated output links should work with same-origin `/outputs/...`
- no production dependency on a fixed host or port in frontend code

#### 3. Frontend validation to add or update
Potential scope:
- add or update a minimal test around URL construction if extraction into a helper is needed
- otherwise keep change minimal and rely on existing component/test coverage plus build and lint

Validation targets:
- `npm run build`
- `npm run test`
- `npm run lint`

### Phase 3: Windows packaging artifacts
Purpose: prepare the project to build a distributable Windows app on a Windows machine.

#### 1. Add PyInstaller spec file
Create a spec that packages:
- the packaged launcher entrypoint
- backend Python modules
- `ui/dist` static frontend assets
- bundled FFmpeg binaries
- OpenCV dependencies required by `cv2`

Expected packaging mode:
- `PyInstaller --onedir`

Why `onedir`:
- easier handling of OpenCV DLLs
- easier inclusion of FFmpeg binaries
- simpler troubleshooting than one-file packaging

#### 2. Add installer script for Inno Setup
Create an `.iss` script that:
- installs the packaged app into `Program Files`
- creates desktop and Start Menu shortcuts
- registers an uninstaller
- optionally offers launch-after-install

Expected installer inputs:
- packaged folder created by PyInstaller on Windows
- app icon and metadata if available

#### 3. Choose concrete packaging file locations
Planned structure:
- keep build/packaging helpers under `scripts/`
- keep the step-by-step user guide as a separate root-level `.txt` file for easy access

Recommended artifact names:
- `scripts/run_packaged.py`
- `scripts/windows_installer.iss` or `scripts/windows/windows_installer.iss`
- `video_auto_cutter.spec` or `scripts/windows/video_auto_cutter.spec`
- `windows-installer-steps.txt`

Final filenames can be adjusted during implementation if existing repo conventions suggest a better fit.

### Phase 4: Documentation deliverable
Purpose: give the user a direct Windows build recipe.

Create a separate plain text file with:
- prerequisites on Windows
- where to place FFmpeg binaries
- how to build the frontend
- how to run PyInstaller
- how to run Inno Setup
- where the final installer output appears
- common failure points such as missing DLLs or SmartScreen warnings

This file is explicitly requested and should be created during implementation.

## Risks To Account For During Implementation
### FFmpeg licensing
Current encoding uses `libx264` and `aac`, so commercial redistribution requires license review.
Implementation may prepare packaging, but legal readiness still remains a separate release gate.

### Unsigned binaries
Even a technically correct installer may trigger SmartScreen until code signing is added.
This should be documented in the Windows steps file.

### OpenCV packaging complexity
`opencv-python` may require PyInstaller data/DLL collection adjustments.
The spec file should be written with this in mind instead of assuming a trivial package.

## Execution Order
1. Refactor backend runtime/config path handling.
2. Add bundled FFmpeg resolution.
3. Add production frontend static serving in FastAPI.
4. Add packaged launcher entrypoint.
5. Update backend tests and run backend validation.
6. Replace frontend hardcoded API/output base URL behavior.
7. Run frontend build, tests, and lint.
8. Add PyInstaller spec.
9. Add Inno Setup script.
10. Create `windows-installer-steps.txt`.
11. Summarize what is implemented versus what still requires a Windows machine to execute.

## Definition Of Done For Implementation
Implementation will be considered complete when:
- the codebase supports same-origin production serving through FastAPI
- the frontend no longer depends on a hardcoded backend URL
- runtime directories are production-safe for a Windows install
- FFmpeg path resolution supports bundled binaries
- a packaged launcher entrypoint exists
- a PyInstaller spec exists
- an Inno Setup script exists
- a separate `windows-installer-steps.txt` file exists with clear build steps
- targeted tests and linters pass where applicable in this environment

## Final Recommendation
Proceed with a browser-based packaged local app for v1, not a desktop shell.
Build the final Windows executable and installer on Windows or in Windows CI, but implement all project-side packaging foundations in this repository first.
