# Cancel Processing Button Plan

## Goal
Add a cancel button that appears only while processing is running, and make cancellation flow through the existing local queue -> API job -> polling architecture with the smallest safe change.

## Current State
- Backend jobs are created in `api/routes/process.py` and stored in-memory by `api/services/job_store.py`.
- Polling uses `GET /jobs/{job_id}` and currently recognizes `queued`, `processing`, `success`, and `error` from `app/schemas.py`.
- Background work is executed by `api/services/processing_service.py`, which calls `VideoProcessor.process(...)`.
- Chunk rendering happens in `app/video/splitter.py`, and each FFmpeg call is blocking via `subprocess.run(...)` in `app/video/ffmpeg.py`.
- Frontend queue orchestration is in `ui/src/App.jsx`; controls are rendered by `ui/src/components/Controls.jsx`.
- Polling currently stops only on `success` or `error`.

## Recommended Scope
Implement cooperative cancellation for the active processing job.

Expected behavior:
- The cancel button is visible only while processing is running.
- Clicking cancel sends a backend cancel request for the active job.
- The current item transitions to a cancelled terminal state with a clear message.
- Polling stops when the job becomes cancelled.
- Cancelling the active job stops the whole running batch queue.
- Partial outputs for the cancelled job should be removed to avoid showing incomplete results.

Important limitation:
- With the current blocking `subprocess.run(...)`, cancellation cannot reliably interrupt an FFmpeg command already in progress.
- The first implementation should therefore cancel at safe checkpoints: before processing starts, between processing stages, and between chunk renders.
- If hard mid-chunk abort is required later, `app/video/ffmpeg.py` will need a controllable `subprocess.Popen(...)`-based runner and process-handle propagation.

## Planned Changes

### 1. Extend backend job state and cancel metadata
Files:
- `app/schemas.py`
- `api/services/job_store.py`

Plan:
- Add a terminal `cancelled` job state.
- Add a lightweight cancel flag in stored job data, such as `cancelRequested: bool`.
- Add `JobStore` helpers for requesting cancellation and reading that flag safely under the existing lock.
- Keep the API payload shape compatible with existing polling, only extending it where needed.

## 2. Add a cancel endpoint
Files:
- `api/routes/process.py`

Plan:
- Add `POST /jobs/{job_id}/cancel`.
- Return `404` for unknown jobs.
- Make cancellation idempotent for terminal jobs so repeated clicks or late requests do not create unstable behavior.
- Update the stored job message immediately so the UI can reflect that cancellation is in progress or complete as soon as possible.

## 3. Add backend cooperative cancellation handling
Files:
- `api/services/processing_service.py`
- `app/video/processor.py`
- `app/video/splitter.py`
- possibly `app/utils/files.py`

Plan:
- Introduce a small internal cancellation exception or explicit cancellation check path.
- Pass a `should_cancel` callback from `process_job(...)` into `VideoProcessor.process(...)`.
- Check cancellation:
  - before expensive preparation work completes,
  - before chunk splitting begins,
  - before each chunk FFmpeg invocation,
  - before final success is written back to the job store.
- When cancellation is detected:
  - mark the job as `cancelled`,
  - set a translated runtime message such as `Processing cancelled.`,
  - avoid overwriting the job later with `success` or `error`.
- Clean up the cancelled job output directory so incomplete clips do not remain in `/outputs/<job_id>/`.

## 4. Preserve deterministic status precedence
Files:
- `api/services/processing_service.py`
- `api/services/job_store.py`

Plan:
- Make terminal state writes deterministic so a late cancel cannot overwrite a completed success, and a completed success cannot overwrite an already-cancelled job.
- Treat cancellation as a normal non-error terminal outcome, not as `error`.

## 5. Add frontend cancel API support
Files:
- `ui/src/api/client.js`
- `ui/src/config/constants.js`

Plan:
- Add a `cancelJob(jobId)` client helper.
- Extend `QUEUE_STATUS` with `cancelled`.
- Keep status strings centralized with the existing constants pattern.

## 6. Update frontend queue orchestration
Files:
- `ui/src/App.jsx`

Plan:
- Add a cancel handler for the currently active backend job.
- Keep the cancel action enabled while other editing controls remain disabled.
- Update polling stop conditions so `waitForCompletion(...)` returns on `cancelled`.
- Ensure a cancelled item does not get remapped to generic failure text by the current catch path.
- Stop the remaining batch immediately after the current item is cancelled.
- Track this behavior explicitly in `handleStartProcessing()` so the loop exits deterministically and does not proceed accidentally.

## 7. Render the cancel button only during active processing
Files:
- `ui/src/components/Controls.jsx`
- possibly `ui/src/App.css`

Plan:
- Add a secondary action button next to or instead of the start button while processing is active.
- Show it only when there is an active item and the app is currently running.
- Keep the start button hidden or disabled during processing to avoid conflicting actions.
- Add only the minimal styling needed to fit the existing controls layout.

## 8. Add copy and translation coverage
Files:
- `ui/src/i18n/translations.js`

Plan:
- Add button label text for `Cancel processing`.
- Add runtime messages for `Cancelling processing.` if used and `Processing cancelled.`.
- Add localized queue-state labels for `cancelled`.
- Keep all new UI and runtime strings in English source keys, following the project rule.

## 9. Update tests
Files:

- `tests/app/test_processor.py`

Planned coverage:
- job store records and exposes cancellation requests
- cancel endpoint returns expected statuses and updates stored jobs
- processing service marks cancelled jobs correctly and still cleans temp uploads
- processor/splitter stop at cancellation checkpoints without reporting success
- frontend controls render the cancel button only during active processing

- frontend queue loop stops after cancellation and does not continue to later files
